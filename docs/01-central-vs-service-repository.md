# 服务仓与中央领域仓

## 本节目标

区分运行时代码事实源与领域控制平面。

## 前置输入

选择一个熟悉的服务仓，列出代码、测试、部署、日志和领域文档。

## 为什么要做

若把服务代码复制进中央仓，多仓历史、Owner 和发布边界会被破坏；中央仓应保存稳定事实和导航。

## 操作步骤

把材料分成服务仓保留、中央仓沉淀、动态事实源引用三类；写出中央仓非目标。

## 关键文件解析

根 `AGENTS.md` 是路由，不是所有知识正文；`services/` 是挂载点，不是代码归档目录。

## 设计取舍

中央仓保持轻量，代码、日志、Trace 和配置正文留在原始事实源。

## 验证命令与预期结果

检查分类表中每项都有唯一去向；运行 `python3 -m central_repo_scaffold inspect --config examples/domain.yaml` 查看边界摘要。

## 常见错误及根因

把中央仓理解为 monorepo 会导致重复代码和错误提交边界；根因是没有区分控制平面与执行平面。

## 学员练习

为自己的领域写三条“负责”和三条“不负责”。

## 完成标准

能解释为什么中央仓不是 README 集合、向量库或业务代码仓。
